## 2. Module Overview

The Diagnostic Classifier trains supervised binary classifiers on DNA methylation features (single CpGs or CpG panels) to discriminate a reference phenotype class from a comparison ("disease") class, and evaluates them on held-out internal and (where available) external cohorts. Six algorithm families are offered, each its own physical tab: **Logistic Regression, Elastic Net, Support Vector Machine, Random Forest, Gradient Boosting/XGBoost, k-Nearest Neighbors** (`DXM_MODEL_SPECS`, `mod_methyl_diagnostic.R:437–530`). Every model shares one generic Setup → Parameters → Results (train/CV) → Test → ROC/AUC → Diagnostics layout, generated by a single UI builder (`dxm_render_model_panel`, lines 552–618) and a single server registrar (`dxm_register_model_server`, lines 665–791), so behaviour is guaranteed identical across the six models — only `spec$fit()` and `spec$params_ui()` differ per model (comment, lines 428–435).

## 3. Diagnostic Classifier Purpose

Per the module config description (`mod_methyl_diagnostic_config`, line 37): *"Trains diagnostic classifiers (logistic regression, elastic net, SVM, random forest, XGBoost, kNN) on single CpGs or a panel, with cross-validated tuning. Works on the preloaded dataset or your own upload."* The scientific question is: **given a sample's methylation level(s) at a chosen CpG or CpG panel, can a classifier discriminate disease-group samples (e.g., "RA") from reference-group samples (e.g., "Control"), and how well does that discrimination generalize to unseen internal and independent-cohort samples?**

## 5. Input Data Architecture

Two mutually exclusive data-source modes, chosen on **Data & Setup** (`radioButtons(ns("data_mode"), ...)`, lines 837–839):

### 5a. Preloaded mode
- Source objects: `gse42861_internal_panel_celltype_adjusted.rds` (internal, all 689 samples/both sexes) and `gse111942_external_panel.rds` (external, 43 samples, all female) — loaded once per process and cached by `load_default_diagnostic_train_test()` (`global.R:679–692`), gated by `METH_DIAG_DATA_AVAILABLE` (`data_paths.R`, referenced `global.R:671`).
- Provenance, per `global.R:653–670`: GSE42861 reprocessed from raw IDATs via `minfi::preprocessNoob()` and granulocyte-adjusted (`lm(M ~ Neutro + Eosino)` per CpG) — **not** the main pipeline's normalization — specifically to be comparable to the GSE111942 external cohort. Both are restricted to the same panel CpGs (21 total, per that comment).
- User picks a **sex stratum** (Female/Male, `radioButtons(ns("sex_stratum"))`, line 842); External Test Data exists only for the female stratum (all 43 GSE111942 samples are female — `global.R:666`, enforced in-app at `mod_methyl_diagnostic.R:905–914`).

### 5b. Upload mode
- `fileInput(ns("upload_matrix"))`: CpG-rows × sample-columns CSV/TSV, parsed by `methyl_parse_matrix()` (`parse_upload.R:11–37`) — first column is treated as the probe ID, duplicate probe IDs rejected, all other columns coerced to numeric.
- `radioButtons(ns("upload_scale"))`: declares whether the uploaded matrix is **Beta-value** or **M-value** scale (line 848) — this is a user assertion, not detected from the data.
- `fileInput(ns("upload_sheet"))`: one row per sample, parsed by `methyl_parse_sample_sheet()` (`parse_upload.R:40–46`), matched to matrix columns by `methyl_sheet_sample_ids()` (`qc.R:456–461`, matches a `sample`/`Sample`/`sample_id`/`Sample_ID` column, else falls back to positional row order if row counts match, else `rownames(sheet)`).
- Phenotype/class column chosen via `selectInput(ns("upload_pheno_col"))`, auto-guessed by regex `class|phenotype|group|status|disease` (line 876).

Both modes converge on the same internal representation: `dxm$train_X` / `dxm$test_internal_X` (data frames, samples × CpGs, **M-value scale**), `dxm$train_y` / `dxm$test_internal_y` (two-level factors `Class0`/`Class1`), and optionally `dxm$test_external_X`/`dxm$test_external_y` (preloaded/female-stratum only).

## 6. End-to-End Workflow

Only steps actually present in the code are listed; absent steps are stated explicitly.

1. **Input methylation data** — preloaded RDS panel or user-uploaded matrix + sample sheet (§5).
2. **Quality control** — *partially implemented as a validation checklist, not a corrective QC pipeline* (see §9). `dxm_validate_checklist()` (lines 77–113) reports duplicate samples/CpGs, missing values, non-numeric columns, constant features, near-zero-variance features, class balance, missing phenotype labels, train/test feature overlap, minimum per-class N — but **does not itself remove or correct** any flagged issue; it is descriptive only.
3. **Data validation** — `observeEvent(input$validate_btn, ...)` (lines 880–952): enforces non-empty distinct class labels, minimum stratum sample count (>20 preloaded, >10 shared IDs / ≥6 per class for upload), builds `dxm$train_X`/`test_internal_X`(/`test_external_X`).
4. **Preprocessing / transformation** — beta→M-value conversion, `dxm_beta_to_m()` (lines 47–50): clip beta to `[1e-6, 1-1e-6]`, then `log2(b/(1-b))`. Applied to the **entire filtered cohort** (train+internal-test, and separately external-test) *before* the train/test split is drawn (line 900, then split at lines 898–902) — see §9 for why this specific transform does not constitute leakage.
5. **Normalization** — **no batch-effect, quantile, or distributional normalization is implemented in this module.** The only per-value transform is the M-value conversion above. See §9/§10.
6. **Feature selection** — **not performed live by this module.** The module only *ingests* an already-chosen CpG or panel from one of four sources (§8, Feature Source tab): Methylomics WGCNA (published module-assignment table or upload), Methylomics Feature Selection (published ensemble-vote table or that module's own RDS export), an uploaded CpG list, or manual selection. No LASSO/Boruta/RFE/etc. selection algorithm is run inside `mod_methyl_diagnostic.R` itself.
7. **Training/validation split** — one stratified split per validation, `caret::createDataPartition(y_all, p = train_frac, list = FALSE)` (lines 899, 938), seeded (`input$dxm_seed`, default 42). `train_frac` defaults to 0.75 (line 855), matching script09's own 75/25 split per the `global.R:662–663` provenance comment.
8. **Classifier training** — one of six algorithms, `spec$fit()` (§10/§13), tuned via repeated k-fold CV (`caret::trainControl(method="repeatedcv", ...)`, lines 137–148) for the five caret-based models, or a manual CV grid search via `xgboost::xgb.cv()` for Gradient Boosting/XGBoost (lines 175–210).
9. **Prediction** — `dxm_predict_prob()` (lines 212–219): predicted probability of the comparison ("Class1") class, on training data, internal test data, and (if available) external test data.
10. **Performance evaluation** — ROC/AUC (`pROC::roc`, DeLong or bootstrap CI), confusion-matrix-derived metrics (accuracy, balanced accuracy, sensitivity, specificity, precision, NPV, F1, MCC), Brier score, PR-AUC (`PRROC::pr.curve`).
11. **Diagnostic metrics** — calibration curve + Brier score + a fitted-slope/intercept logistic recalibration diagnostic (`dxm_calibration`, lines 310–322); a learning curve (train-size-vs-AUC, `dxm_learning_curve`, lines 339–351); an automatically-worded overfitting note comparing train vs. CV vs. test AUC (`dxm_overfitting_note`, lines 327–337).
12. **Visualisation** — ROC curves (train/CV/test/external), a fold-resolved CV ROC plot, a calibration plot, a learning-curve plot, and a cross-run ROC comparison plot (§14).
13. **Final results/download** — per-model ROC PNG download; cross-model metrics CSV (Export tab and Model Comparison tab); selected feature-panel CSV.

**Not implemented in the current code:**
- No independent, out-of-app validation cohort beyond the one bundled external RDS (female stratum only).
- No nested cross-validation (feature selection, where it happens at all, is entirely upstream/offline and never re-run inside a CV fold — because no feature selection happens inside this module at all).
- No batch-effect correction, quantile normalization, or missing-value imputation routine (missing values are only **reported**, never imputed, by `dxm_validate_checklist`).
- No automatic zero-variance feature removal (near-zero-variance features are **reported**, `nearZeroVar()`, line 94, but not dropped).
- No confidence intervals on any metric except AUC (`pROC::ci.auc`, DeLong or bootstrap fallback, lines 229–230); sensitivity/specificity/accuracy/F1/etc. are reported as point estimates only.
- Platt-scaling recalibration functions exist (`dxm_platt_fit`/`dxm_platt_apply`, lines 324–325) but are **never called** anywhere in the file — dead code, not wired to any UI element (verified: these two identifiers appear only at their own definition).

## 7. Detailed Tab-by-Tab Documentation

### Tab 1 — Data & Setup
**Purpose:** choose a data source, define the two-class contrast, set the train fraction and random seed, and validate the resulting matrices before anything else in the module becomes usable.

**User Inputs** (`output$setup_ui`, lines 834–869): `data_mode` (preloaded/upload radio), `sex_stratum` (preloaded only), `upload_matrix`/`upload_scale`/`upload_sheet`/`upload_pheno_col` (upload only), `ref_level`/`comp_level` (free-text class labels, defaults "Control"/"RA"), `train_frac` (numeric, 0.5–0.9, default 0.75), `dxm_seed` (numeric, default 42), and the `validate_btn` action button.

**Input data:** the raw preloaded RDS pair, or the user's uploaded matrix + sheet (§5).

**Processing:** `observeEvent(input$validate_btn, ...)` (lines 880–952) — described in §6, steps 3–4. Every downstream tab is gated on `dxm$validated` being `TRUE` (e.g., `req(dxm$validated)` at line 962, 1090; `dxm_render_model_panel` line 553 shows a placeholder otherwise).

**Functions used:** `load_default_diagnostic_train_test()` (`global.R:679`), `dxm_beta_to_m()`, `caret::createDataPartition()`, `methyl_parse_matrix()`, `methyl_parse_sample_sheet()`, `methyl_sheet_sample_ids()`, `dxm_validate_checklist()`.

**Output data:** `dxm$train_X`/`train_y`, `dxm$test_internal_X`/`test_internal_y`, `dxm$test_external_X`/`test_external_y` (conditionally), `dxm$all_cpgs`, `dxm$validation_report` (a data frame rendered as `output$validation_table`).

**Scientific interpretation:** this is the only point in the workflow where the disease contrast, cohort, and stratum are fixed; every later tab operates on exactly these matrices.

**Connection to other tabs:** feeds `dxm` (a `reactiveValues`) to every other tab; re-running `validate_btn` resets `feat$source`/`feat$table`/`feat$selected` (line 950), invalidating any previously loaded feature panel.

### Tab 2 — Feature Source
**Purpose:** choose which CpG(s) will be modeled, from one of four sources.

**User Inputs** (`output$feature_ui`, lines 961–1000): `feature_source` (radio: `wgcna`/`featureselection`/`uploaded`/`manual`), plus source-specific controls: `wgcna_module`/`wgcna_top_n` or `wgcna_upload` (WGCNA); `fs_min_votes`/`fs_top_n` or `fs_upload` (Feature Selection); `panel_upload` (Uploaded); `manual_cpg_select` (Manual, a searchable multi-select over `dxm$all_cpgs`); and one load button per source.

**Input data:**
- *WGCNA, preloaded:* `load_default_wgcna_module_assignment(dxm$sex)` (`global.R:515–521`) — the **published, offline** module-assignment CSV, the same one `mod_methyl_wgcna.R`'s own "Compare with published results" panel reads (module header comment, lines 24–27). *WGCNA, upload:* a CSV with a `cpg`/`CpG`/`probe`/`ID` column, from that module's own download.
- *Feature Selection, preloaded:* `load_default_diagnostic_ensemble_votes(dxm$sex)` (`global.R:621–627`) — script07's majority-vote panel (`n_votes ≥ 2` of LASSO/Boruta/SVM-RFE, per `global.R:614–617`). *Feature Selection, upload:* an RDS produced by `fs_model_export()` (`mod_methyl_featureselection.R:1761–1785`), validated by `obj$module == "mod_methyl_featureselection"` (line 1048) and read from `obj$final_panel$cpg_ids`.
- *Uploaded panel:* a CSV/TXT of CpG IDs, parsed by `data.table::fread` or `methyl_parse_probe_list()` (`parse_upload.R:50–57`).
- *Manual:* direct multi-select from `dxm$all_cpgs`.

**Processing:** each source's `observeEvent` (lines 1006–1085) intersects the candidate IDs with `dxm$all_cpgs` (i.e., CpGs actually present in the *currently active* train matrix), optionally truncates to a top-N, and writes `feat$source`, `feat$table`, `feat$selected`.

**Functions used:** `load_default_wgcna_module_assignment()`, `load_default_diagnostic_ensemble_votes()`, `readRDS()`, `data.table::fread()`, `methyl_parse_probe_list()`.

**Output data:** `feat$selected` (character vector of CpG IDs), `feat$table` (annotated data frame), `feat$source` (one of `"wgcna"`/`"featureselection"`/`"uploaded"`/`"manual"`).

**Scientific interpretation:** this tab does not *choose* biomarkers — it *imports* a panel already chosen by an upstream, published/offline analysis (WGCNA module membership, or a supervised feature-selection ensemble), or lets the user hand-pick CpGs. See §12 for why this matters for the leakage audit.

**Connection to other tabs:** `feat$selected` feeds directly into Filters & Parameters (Combined mode) and into every model tab's "Combined panel" run.

### Tab 3 — Filters & Parameters
**Purpose:** choose single-CpG vs. combined-panel analysis, inspect class balance, configure imbalance handling, cross-validation, hyperparameter search strategy, and the classification-threshold rule; optionally dispatch a model run without visiting that model's own tab.

**User Inputs** (`output$filters_ui`, lines 1089–1125): `analysis_type` (`single`/`combined`), `single_cpg` (choices = `feat$selected` if loaded, else all of `dxm$all_cpgs` — **note:** single-CpG mode can bypass Feature Source entirely), `imbalance_mode` (`none`/`weighted`/`smote`), `cv_folds` (3–20, default 10), `cv_repeats` (1–10, default 1), `search_method` (`grid`/`random`), `threshold_strategy` (`default`/`youden`/`sensitivity`/`specificity`), `run_model_choice` + `run_selected_model_btn`.

**Processing:** purely configuration; `output$class_balance_table` (lines 1127–1133) is a live cross-tab of `dxm$train_y`. `run_selected_model_btn` (lines 1150–1157) calls the exact same `dxm_do_run_model()` used by each model tab's own "Run Model" button, then switches the active tab to that model's tab (`updateTabsetPanel`).

**Functions used:** `dxm_do_run_model()`, `dxm_cv_control()` (indirectly, inside the run).

**Output data:** none produced directly on this tab besides the class-balance table; its widgets are read by `dxm_do_run_model()`/`dxm_cv_control()` when a run is triggered from *any* tab.

**Scientific interpretation:** this tab is the single point of truth for every hyperparameter-search and resampling setting applied uniformly across all six models.

**Connection to other tabs:** every model tab's `_run_btn` observer (line 681–684) reads these same `input$...` values; this tab and the six model tabs are therefore tightly coupled through shared `input` state, not through a passed object.

### Tabs 4–9 — Logistic Regression / Elastic Net / Support Vector Machine / Random Forest / Gradient Boosting / XGBoost / k-Nearest Neighbors

These six tabs share one generic implementation (`dxm_render_model_panel`, `dxm_do_run_model`, `dxm_register_model_server`), so they are documented together; per-model differences (algorithm, hyperparameters, preprocessing) are in §13.

**Purpose:** fit one classifier on the active feature set, cross-validate it, evaluate it on test data, and visualize performance.

**User Inputs:** per-model hyperparameter controls (`spec$params_ui`, §13), plus four generic action buttons per tab: `{mid}_run_btn`, `{mid}_test_btn`, `{mid}_roc_btn`, `{mid}_calib_btn`, `{mid}_lc_btn` (lines 570, 582, 593, 611, 614).

**Input data:** `dxm$train_X`/`train_y` restricted to the active CpG ID set (`dxm_active_ids()`, lines 658–663: `input$single_cpg` if `analysis_type == "single"`, else `feat$selected`), intersected with `colnames(dxm$train_X)` (line 625).

**Processing (`dxm_do_run_model`, lines 624–656):**
1. Resolve active feature IDs; `validate(need(length(ids) > 0, ...))` if none match.
2. Build `ctrl <- dxm_cv_control(input)` (repeated CV control, imbalance sampling wired in).
3. `spec$fit(Xtr, ytr, input, mid, ctrl, seed)` — the one per-model difference.
4. Compute training-set predicted probabilities, training ROC bundle, CV ROC (`dxm_cv_roc_from_fit()` for caret models — reuses caret's own held-out fold predictions, i.e., genuinely out-of-fold; `dxm_xgb_cv_roc()` for the native XGBoost path — a *separate*, self-implemented `k`-fold loop).
5. Pick a classification threshold from the **training ROC only** (`dxm_pick_threshold()`, never from test data — comment, line 273).
6. Compute training metrics/confusion matrix.
7. Reset every downstream (test/ROC/calibration/learning-curve) state, so stale results from a previous run cannot remain visible after a re-run (line 649–651).

`{mid}_test_btn` (lines 686–715): applies the *already-fitted* model to `dxm$test_internal_X` (and, if feature-compatible, `dxm$test_external_X`), computes test metrics/confusion matrices at the **training-derived threshold**, records the run into `runs[[key]]` (used by Model Comparison), and writes a compact summary into `results$diagnostic` (i.e., `methyl_results$diagnostic` — consumed generically by `build_mx_context()`/`.format_results_block()` in `R/submodules_registry.R:125,179`, which builds the ArthoChat assistant's session-context text; **not** dead code, though it is a "last model wins" single-slot summary, not a per-model history).

`{mid}_roc_btn`: reveals four ROC plots (train, CV-fold-resolved, test, external if present). `{mid}_calib_btn`: computes/plots a calibration curve from the **pooled out-of-fold CV predictions** (`ms$cv_roc$pooled`, not test data). `{mid}_lc_btn`: refits the same model at four training-fraction subsets (40/60/80/100%) with 5-fold CV to trace an AUC-vs-sample-size curve.

**Functions used:** `dxm_do_run_model`, `dxm_predict_prob`, `dxm_roc_bundle`, `dxm_cv_roc_from_fit`/`dxm_xgb_cv_roc`, `dxm_pick_threshold`, `dxm_metrics_bundle`, `dxm_confusion`, `dxm_calibration`, `dxm_learning_curve`, `dxm_overfitting_note`, `dxm_plot_roc`, `dxm_plot_cv_roc`, `dxm_plot_calibration`, `dxm_plot_learning_curve`, `dxm_metrics_display`.

**Output data:** a `train` object (class `"train"` or `"xgb.Booster"`), probability vectors, ROC bundles (`pROC::roc` objects + AUC + CI + coordinate table), confusion-matrix-derived metric lists, a calibration table, a learning-curve data frame, four/five plots, one CSV download (`{mid}_roc_png`, an image not a table — `downloadHandler`, lines 783–786).

**Scientific interpretation:** each tab answers "how well does *this* algorithm, on *this* feature set, separate the two classes, and does its performance hold up out-of-sample?"

**Connection to other tabs:** reads `dxm`/`feat`/shared `input` from Tabs 1–3; on successful test evaluation, writes into the shared `runs` reactiveValues consumed by Model Comparison (Tab 10) and Export (Tab 12).

### Tab 10 — Model Comparison
**Purpose:** compare every completed (trained **and** test-evaluated) run, across models and across single-CpG vs. combined-panel analyses.

**User Inputs:** `compare_select` (multi-select of run keys), `compare_curve` (`test`/`train`/`cv`), `compare_roc_btn`; `svp_model` (model picker for the single-vs-panel view).

**Input data:** `runs` (a `reactiveValues` keyed by `paste(mid, analysis_type, feature_ids)`, line 702 — so re-running the *same* model on the *same* feature set overwrites its prior entry, while a different feature set for the same model creates a new row).

**Processing:** `output$compare_table` (lines 1187–1197) tabulates Train/CV/Test/External AUC, threshold, and timestamp per run. A prominent in-app caveat (lines 1166–1167) states: *"'Test AUC' (internal) is drawn from the same cohort the WGCNA- and Feature-Selection-derived CpG panels were originally selected on, so it can be optimistically biased for those two feature sources. 'External AUC', where available, is a fully independent held-out cohort and is the more trustworthy headline number."* This is the module's own, code-present acknowledgement of the cross-cohort feature-selection provenance issue analyzed in §12.

**Functions used:** none beyond base/DT/ggplot2 rendering of already-computed `runs` entries; `dxm_plot_roc_compare()` for the comparison plot.

**Output data:** a comparison table (downloadable CSV, `compare_download`), an overlaid ROC plot, a single-vs-panel sub-table.

**Connection to other tabs:** purely a read-only aggregator over what Tabs 4–9 have already written to `runs`.

## 8. Complete Function Inventory

### 8.1 Small shared utilities

| Function | Source | Type | Purpose | Input | Processing | Output | Downstream use | Scientific relevance |

## 9. Normalisation Audit

**What the code actually does:**
- The *only* value transformation applied to methylation data inside this module is the beta→M-value logit transform, `dxm_beta_to_m()` (lines 47–50), applied identically to preloaded and uploaded beta-scale data (upload: line 934, `if (identical(input$upload_scale, "m")) mat else dxm_beta_to_m(mat)` — uploaded M-value data is *not* re-transformed, trusting the user's declared scale).
- This transform is **row/sample-independent and parameter-free**: each value is mapped by a fixed formula using only its own clipped value — it does not compute or use any statistic (mean, SD, quantile, min/max) across samples or across CpGs. Consequently, applying it to the full cohort (train+test combined) *before* splitting introduces **no information leakage**, because no cross-sample information is estimated from data that later becomes the held-out set. This directly addresses one of the leakage-audit questions in §12.
- Orientation: `dxm_beta_to_m()` receives a matrix with **CpGs as rows and samples as columns** (the internal RDS format, `beta_sub[, keep]`), consistent with standard methylation-array matrix conventions; it is then explicitly **transposed** (`t(...)`) when building the samples-as-rows/CpGs-as-columns `Xm` data frame that `caret`/`glmnet`/etc. expect (lines 900, 909, 939). The transpose is applied identically for internal, external, and uploaded matrices.
- **No further normalization is implemented**: no quantile normalization, no BMIQ/SWAN/functional normalization, no batch-effect correction (e.g., ComBat), no cross-array-type harmonization. This is scientifically consistent with the module's design: the preloaded data has *already* been normalized upstream (Noob, per `global.R:658`) before ever reaching this module, and re-normalizing a 21-CpG panel-only slice in-app would not reproduce array-wide normalization in any case (functional/quantile normalization methods require the full array's probe distribution, not a small panel).
- **Model-internal scaling** (a distinct, later step from "normalization" but relevant to the same audit): `preProcess = c("center","scale")` is passed to `caret::train()` for **SVM and kNN only** (lines 492, 528) — the two distance/margin-based algorithms whose optimization is scale-sensitive. Random Forest, XGBoost, and the `glm`/`glmnet`-based Logistic Regression/Elastic Net paths receive `preProcess = NULL` (default, e.g. line 452, 474, 507) — appropriate, since tree ensembles are scale-invariant, and `glmnet`'s own fitting internally standardizes predictors by default regardless of caret's `preProcess` argument (a `glmnet` package default, not something this module code sets or overrides).
- `caret::train()`'s `preProcess` step is fit *only inside each resampling iteration's training partition*, per caret's own documented resampling contract — i.e., center/scale statistics for SVM/kNN are re-estimated per CV fold from that fold's training rows only, and applied to the held-out fold via the already-fitted transform, not re-fit on it. The same applies to the outer internal/external test evaluation: `dxm_predict_prob()` calls `predict(fit$model, newdata=X)`, reusing the scaling parameters learned from the training set — never refitting them on test data.

**What a scientifically complete implementation would additionally do** (see also §19, §26): array-wide normalization prior to panel extraction (already done upstream, outside this module's control); explicit imputation of missing methylation values (currently reported, not corrected — a listwise/columnwise strategy is left to the user's upstream data preparation); explicit removal (not just reporting) of zero-variance/near-zero-variance CpGs before fitting.

**Timing/orientation/leakage summary table:**

| Question | Finding |
|---|---|
| Is normalization actually implemented? | Only a fixed, parameter-free beta→M-value transform; no distributional/batch normalization |
| Where does it occur? | `dxm_beta_to_m()`, called once per validation, before the train/test split (lines 900, 909, 934, 939) |
| Rows = CpGs or samples in the raw matrix? | CpGs are rows in the raw beta matrix; transposed to samples-as-rows before modeling |
| Applied across samples or across features? | Neither — it is elementwise, not a per-sample or per-feature statistic |
| Before or after train/test split? | Before — but leakage-safe because it is elementwise (see above) |
| Same transform applied to train and test? | Yes, identically, including external test |
| Model-internal scaling (center/scale) timing | Fit per-CV-fold and on the full training set only; applied (not refit) to internal/external test |
| Missing values | Detected/reported (`dxm_validate_checklist`), never imputed |
| Zero-variance features | Detected/reported (`nearZeroVar`, constant-column check), never dropped |
| Scale appropriateness | M-values used for modeling per the module's own header comment (never beta-values, never covariate-adjusted residuals) — matches standard methylomics-ML practice |
| Reactive recalculation risk | Re-running `validate_btn` fully rebuilds `dxm$train_X` etc. from scratch (deterministic given the same seed/inputs) — no risk of a stale, partially-updated matrix, since the whole `dxm` block is reassigned in one observer pass |
| Matrix dimensions as expected? | `Xm` has `nrow = n_samples`, `ncol = n_CpGs` after transpose; train/test row counts sum to the filtered cohort size by construction of `caret::createDataPartition`'s complement split |

## 10. Preprocessing Audit

Beyond §9's normalization/scaling findings: **filtering** is limited to what `dxm_validate_checklist` reports (duplicates, missing values, non-numeric, constant, near-zero-variance) — none of these are automatically removed. **Missing-value handling**: no imputation function exists anywhere in the file; if `dxm$train_X` contains `NA`s, downstream `caret::train()`/`glmnet`/etc. calls would either error or (for tree methods with native NA support) behave per-package defaults — the module does not standardize this behavior itself. **Feature scaling** is algorithm-specific and appropriate (§9). **Class encoding**: `Class1`/`Class0` sentinel labels (lines 68–69) sidestep syntactic-validity issues `caret::twoClassSummary` would otherwise raise for arbitrary user-typed class names (e.g., containing spaces) — a deliberate, documented workaround (comment, lines 64–67), with the true class label preserved separately as `dxm$comp_level`/`dxm$ref_level` for display.

## 11. Feature-Selection Audit

**No feature-selection algorithm executes inside this module.** All four "Feature Source" options (§7, Tab 2) either read an already-computed, upstream/offline selection result (WGCNA module membership; a majority-vote ensemble from script07/the Feature Selection module) or accept a user-supplied list (uploaded panel; manual pick). Consequently:
- Feature selection cannot be "nested within cross-validation" here, because it is not part of this module's pipeline at all — the relevant nested-CV concern applies to the *upstream* Feature Selection module, not this one.
- The panel is fixed identically for training, internal test, and external test within a given run (`ids` computed once per `dxm_do_run_model()` call, reused unchanged by the `_test_btn` observer, line 688–689).
- The one selection-adjacent decision made *inside* this module is thresholding an already-computed vote/module table (`fs_min_votes`, `wgcna_top_n`/`fs_top_n`) — a filter on a static, precomputed column, not a live statistical selection procedure.

This is not a leakage risk (nothing incorrect happens to the data), but it is a **functional gap**: a user who selects "SMOTE" expecting it to apply uniformly across all six model tabs will not get that behavior for XGBoost, with no warning shown |

## 13. Machine-Learning Workflow Audit

**Dataset partitioning:** one seeded, stratified 75/25 (default, user-adjustable 50–90%) train/internal-test split per validation (`caret::createDataPartition`, lines 899, 938); optional independent external-test cohort (preloaded, female stratum only). No separate "validation" split distinct from the CV folds used for tuning — hyperparameter tuning uses k-fold (default 10-fold) repeated CV *within* the training partition (`caret::trainControl(method="repeatedcv")`, and the manual `xgboost::xgb.cv()` equivalent).

**Class balance:** reported (`class_balance_table`, `dxm_validate_checklist`'s imbalance-ratio check, ≤3:1 = OK). Handling is user-selectable: `none`; `weighted` (caret: `sampling="up"` — despite the UI label "Class weighting," this is fold-safe **up-sampling**, not a loss-function class-weight, for the five caret-based models; native XGBoost: `scale_pos_weight` — a true loss-function class weight); `smote` (fold-safe SMOTE, caret-based models only — no effect on XGBoost, per §12).

**Feature selection:** none live (§11).

**Model training — six classifiers:**

| Model | Algorithm | Tunable hyperparameters (UI-exposed) | Notes |
|---|---|---|---|
| Logistic Regression | `glmnet` (fixed `alpha` = 0 [ridge] or 1 [lasso], tuned `lambda` from user-entered `C` values, `lambda = 1/C`); **or** plain `glm` if a single CpG is selected (`ncol(X) < 2`) | Penalty type, `C` grid, max iterations, tolerance | glmnet requires ≥2 predictor columns; single-CpG mode falls back to unregularized `glm` (lines 446–447) |
| Elastic Net | `glmnet`, either automatic search (`tuneLength`) or a user-specified `alpha`×`lambda` grid | Auto vs. manual grid, α/λ ranges, search size, max iterations, tolerance | Same single-CpG `glm` fallback |
| Support Vector Machine | `svmLinear`/`svmRadial`/`svmPoly` (caret/kernlab) | Kernel choice, `C`, `sigma` (RBF), `degree`/`scale` (polynomial) | `preProcess = c("center","scale")` |
| Random Forest | `rf` (caret/randomForest) | `ntree`, `mtry` grid, `nodesize`, `maxnodes` | No preprocessing (tree-based) |
| Gradient Boosting/XGBoost | native `xgboost` (not caret's `xgbTree`, per §8.4) | `nrounds` (with early stopping), `eta`, `max_depth`, `min_child_weight`, `subsample`, `colsample_bytree`, `gamma` | Own manual CV grid search (`xgb.cv`), not caret's tuning machinery |
| k-Nearest Neighbors | `knn` (caret) | `k` grid | `preProcess = c("center","scale")`; weights fixed to uniform, distance fixed to Euclidean — the module's own help text (line 524) states this is because the optional `kknn` package (needed for distance-weighting/Minkowski/leaf-size) is not installed in this deployment |

**Model evaluation — metrics actually calculated** (`dxm_metrics_bundle`/`dxm_confusion`, §8.5): Accuracy, Balanced Accuracy, Sensitivity (Recall), Specificity, Precision, NPV, F1, MCC, ROC-AUC (+ DeLong/bootstrap 95% CI), PR-AUC, Brier score, N. **No other metrics are computed** — e.g., no Cohen's kappa, no log-loss beyond Brier, no calibration slope/intercept displayed in the metrics tables (though computed internally by `dxm_calibration` for the plot).

## 14. Statistical and Scientific Correctness Audit

| # | Item | Verdict | Explanation |
|---|---|---|---|
| 1 | Beta→M-value transform for ML input | **PASS** | Mathematically standard (`log2(b/(1-b))`), correctly clipped to avoid infinite values at the boundary; matches established methylomics-ML practice |
| 2 | Algorithm-appropriate scaling (center/scale for SVM/kNN only) | **PASS** | Distance/margin-sensitive models are scaled; scale-invariant models (RF, XGBoost) and internally-standardizing `glmnet` are not redundantly rescaled by caret |
| 3 | CV design (`repeatedcv`, `twoClassSummary`, `savePredictions="final"`) | **PASS** | Appropriate for tuning + honest out-of-fold performance reporting via `dxm_cv_roc_from_fit` |

| 8 | Overfitting note (`dxm_overfitting_note`) | **INFORMATION** | A fixed 0.15-AUC-gap heuristic, not a statistical hypothesis test (e.g., no test of whether the train–test AUC difference is statistically distinguishable from sampling variation) — appropriately framed in the code's own language as descriptive ("suggesting," "broadly consistent"), not as a formal test |

## 15. Reactive and UI Connections Audit

- **Gating:** every tab beyond Data & Setup is gated on `req(dxm$validated)` (lines 962, 1090) or an equivalent early-return (`dxm_render_model_panel`, line 553); the six model tabs cannot render meaningful content before validation, and correctly show a text prompt instead.
- **Run/Test buttons → correct outputs:** each model's `_run_btn` writes into that model's own `ms` (a per-model `reactiveValues` created in a `lapply` closure, lines 1137–1147) — there is no cross-model state bleed, since each `ms` instance is distinct.
- **Stale-result prevention:** `dxm_do_run_model()` explicitly nulls out every downstream field (`test_internal_prob`, `roc_generated`, `calib`, `lc`, etc., lines 649–651) on every new run, so a previous run's test/ROC/calibration/learning-curve results cannot remain visible after re-running with different settings.
- **Output-ID correspondence:** all model-tab outputs are namespaced by `paste0(mid, "_...")` (e.g., `lr_train_metrics_table`, `svm_roc_plot`), generated identically by `dxm_render_model_panel` (which builds the `ns(paste0(mid, ...))` IDs) and `dxm_register_model_server` (which registers `output[[paste0(mid, ...)]]`) — the same naming convention is used on both sides, so IDs match by construction rather than by manual duplication risk.
- **Downloads correspond to displayed results:** the ROC PNG download (`{mid}_roc_png`) re-renders from `ms$last_roc_plot`, the same object most recently drawn on screen (lines 765, 783–786) — not a freshly recomputed plot that could diverge from what's displayed.
- **Validation before analysis:** `dxm_do_run_model()` begins with `validate(need(length(ids) > 0, ...))` (line 626) before touching any data.
- **Error handling:** model-fit failures are caught (`tryCatch`, line 632) and surfaced via `showNotification(type="error")` rather than crashing the app; every plotting function uses `validate(need(...))` guards.
- **Filters & Parameters ↔ model tabs coupling:** the "Run Model" dispatcher on Filters & Parameters and each model tab's own "Run Model" button call the *identical* `dxm_do_run_model()` function (comment, lines 620–623) — confirmed no behavioral divergence between the two entry points.
- **Independent tabs:** Test Data (Tab 11) is purely descriptive and does not depend on, or feed, any model run. The Feature Source tab's "single CpG" list can be populated directly from `dxm$all_cpgs` without ever loading a feature panel (line 1095) — so Filters & Parameters' single-CpG mode is *not strictly dependent* on Tab 2, even though "Combined panel" mode is.

## 16. Tab-to-Tab Connections

- **Data & Setup → everything else:** produces `dxm` (train/test matrices, labels, validation flag), read by all subsequent tabs.
- **Data & Setup → Feature Source:** re-validating resets `feat$source`/`feat$table`/`feat$selected` (line 950), forcing the user to reload a feature panel after any dataset change.
- **Feature Source → Filters & Parameters → model tabs:** `feat$selected` is the combined-panel feature list used by every model's "combined" run; Filters & Parameters additionally exposes `dxm$all_cpgs` directly for single-CpG mode, bypassing Feature Source.
- **Filters & Parameters → model tabs:** every CV/imbalance/threshold/search-method input is read directly by `dxm_do_run_model()`/`dxm_cv_control()` regardless of which tab triggered the run.
- **Model tabs → Model Comparison, Export:** each model's `_test_btn` writes one entry into the shared `runs` store; Model Comparison and Export are pure downstream aggregators/consumers of `runs` and never write back to it.
- **Model tabs → shared ArthoChat context:** each model's `_test_btn` also overwrites `results$diagnostic` (i.e., `methyl_results$diagnostic`) with a single-slot summary (last model run, its AUCs, sex stratum, mode) — consumed by `build_mx_context()`/`.format_results_block()` (`R/submodules_registry.R:125,179`) to build the Methylomics AI-assistant's session context. This is a genuine downstream consumer, not dead code — but because it is a single overwritten slot, it reflects only the *most recently test-evaluated* model, not a full history (that full history lives only in `runs`, which the assistant context does not read).
- **Test Data tab:** connected conceptually (it reports on the same `dxm$train_X`/`test_*_X`) but not functionally wired to any other tab's computation — it is read-only diagnostic display.

## 18. Reproducibility Audit

| Aspect | Controlled? | Detail |
|---|---|---|
| Train/test split | Yes | `set.seed(seed)` immediately before `caret::createDataPartition()` (lines 898, 937); `seed` = `input$dxm_seed`, user-adjustable, default 42 |
| Model fitting (caret path) | Yes, at the top level | `set.seed(seed)` inside `dxm_fit_caret()` (line 158) before `caret::train()`; caret does not receive an explicit per-resample `trainControl(seeds=...)` list, so exact resample-by-resample RNG draws depend on caret's own internal, version-tied RNG consumption sequence rather than being independently pinned |
| Model fitting (XGBoost path) | Yes, per grid candidate | `set.seed(seed)` reset before every `xgb.cv()` call and again before the final `xgb.train()` refit (lines 195, 207) |
| SMOTE fold augmentation | Partially | Runs inside a `set.seed(seed)`-preceded `caret::train()` call, but SMOTE's own random interpolation draws depend on caret's internal RNG consumption order for that fold, not an explicitly pinned per-fold seed |
| Random Forest (`mtry` search, tree randomness) | Partially | Same caveat as the general caret path — reproducible within a fixed R/package-version environment given the top-level seed, not independently pinned per resample |
| Package versions | Not pinned in-code | No `renv`/version-check logic inside this file itself (the project as a whole uses `renv.lock`, outside this module's scope) |
| Preprocessing parameters | Deterministic given the data | Center/scale statistics are a deterministic function of the (seeded) training partition — no additional randomness |

**Limitation:** results are reproducible **given** a fixed R/package-version environment and the same `dxm_seed`, but the module does not use `trainControl(seeds = ...)` to pin every individual resampling iteration's seed explicitly — the standard caveat for any caret-based pipeline that seeds only once before calling `train()`.

## 19. Missing Functionality (Explicit)

- **Not implemented:** any batch-effect correction, quantile/functional/BMIQ normalization, or missing-value imputation.
- **Not implemented:** automatic removal of zero-variance or near-zero-variance features (detected/reported only).
- **Not implemented:** nested cross-validation of any kind (there is no live feature-selection step to nest in the first place).
- **Not implemented:** confidence intervals for any metric other than AUC.
- **Not implemented:** SMOTE or up-sampling for the Gradient Boosting/XGBoost tab (silently no-op; only `scale_pos_weight` applies there).
- **Not implemented:** application of the computed Platt/logistic calibration diagnostic to actually recalibrate displayed probabilities (`dxm_platt_fit`/`dxm_platt_apply` exist but are never called).
- **Not implemented:** distance-weighted or Minkowski-parameterized kNN (disclosed in-app as an optional-package limitation, line 524).
- **Not implemented:** any independent validation cohort beyond the single bundled external RDS (female stratum only; no external cohort exists for the male stratum or for upload mode).
- **Not implemented:** per-run (as opposed to per-module, single-slot) propagation of results into the shared `methyl_results` store consumed by the AI assistant.

## 25. Scientific Interpretation

**Biological data entering the classifier:** DNA methylation levels (originally beta-values, 0–1 proportion methylated) at a small, fixed panel of CpG sites, converted to M-values before modeling. **Diagnostic question:** can methylation at these CpGs discriminate a disease phenotype (default label "RA," configurable) from a reference/control phenotype in whole blood? **Feature:** one CpG's M-value (single-CpG mode) or a vector of M-values across a CpG panel (combined mode). **Outcome/class:** a binary phenotype label supplied by the sample sheet/preloaded metadata, encoded internally as `Class0` (reference) / `Class1` (comparison). **Transformation of methylation features:** beta→M-value logit transform only (§9); no further normalization inside this module. **Selection of informative CpGs:** imported from an already-computed WGCNA co-methylation module, an already-computed multi-method feature-selection ensemble vote, a user-supplied panel, or manual choice — never computed live here. **Classifier training:** one of six standard supervised algorithms, tuned by repeated k-fold CV on the training partition only. **Diagnostic performance evaluation:** ROC/AUC with confidence intervals, a full confusion-matrix metric suite, PR-AUC, Brier score, calibration diagnostics, and a learning curve — computed separately for training, cross-validation, internal test, and (where available) an independent external cohort. **Final results represent:** an estimate of how well a given algorithm/panel combination discriminates the two phenotypes on data it was not fitted on, with the external-cohort number the least biased of the reported figures when the feature panel came from WGCNA or Feature Selection. **Limitations that must be acknowledged:** panel-only training data (21 CpGs total, per upstream provenance) rather than genome-wide; a single, small (n=43, female-only) external validation cohort; no automated correction of missing values or zero-variance features; a fixed-threshold, non-statistical overfitting heuristic; and the cross-cohort feature-provenance caveat for two of the four feature sources (§12).

## 26. Limitations (Consolidated)

1. Only a fixed, parameter-free M-value transform is implemented as "preprocessing" — no batch correction, imputation, or zero-variance removal.
2. No feature-selection algorithm runs live; the module strictly depends on the quality and provenance of upstream/external panels.
3. "Test AUC" for WGCNA/Feature-Selection-sourced panels can be optimistically biased due to cohort overlap with the panel's original selection step (disclosed in-app).
4. Imbalance handling ("weighted"/"SMOTE") does not behave uniformly across all six models (no effect on XGBoost beyond `scale_pos_weight` under "weighted").
5. Threshold strategies targeting a specific sensitivity/specificity can silently fail to reach that target without warning.
6. No confidence intervals beyond AUC.
7. Calibration is diagnosed but never corrected.
8. External validation exists only for the female stratum, n=43, and only in preloaded mode.
9. Reproducibility is guaranteed only within a fixed R/package-version environment; no per-resample seed pinning via `trainControl(seeds=...)`.
10. A single, session-scoped, last-run summary is shared with the AI assistant context, not a full run history.

## 27. Recommended Corrections (Optional — Not Applied)

Per the scope in §1, **no code was changed**. If corrections were to be made in a future, separately scoped change, priority order based on the severity table (§24b) would be: (1) fix the silent threshold-selection fallback; (2) disclose or unify the "weighted"/"SMOTE" behavior difference across models; (3) gate or clearly flag `FAIL`-status validation checks before allowing a run; (4) add bootstrap CIs to the confusion-matrix metrics, especially for the small external cohort; (5) either wire up or remove the unused Platt-calibration functions and other dead helpers.

## 28. XomicShiny-Style Thesis Implementation Paragraph

The Methylomics Diagnostic Classifier submodule comprises twelve tabs — Data & Setup, Feature Source, Filters & Parameters, six per-algorithm model tabs (Logistic Regression, Elastic Net, Support Vector Machine, Random Forest, Gradient Boosting/XGBoost, k-Nearest Neighbors), Model Comparison, Test Data, and Export — implemented in `mod_methyl_diagnostic.R`. It accepts either a preloaded, Noob-renormalized and granulocyte-adjusted 21-CpG panel derived from GSE42861 (with an independent GSE111942 external cohort available for the female stratum) or a user-uploaded probe-by-sample methylation matrix with an accompanying sample sheet. Methylation beta-values are converted to M-values by a fixed, sample-independent logit transform before a seeded, stratified train/test split; CpG or CpG-panel features are ingested — not selected — from published WGCNA module assignments, a majority-vote feature-selection ensemble, an uploaded panel, or manual choice. Each of the six classifiers is fit via `caret::train()` (or, for gradient boosting, a native `xgboost` cross-validated grid search chosen to avoid a version-specific caret/xgboost incompatibility) under repeated k-fold cross-validation, evaluated by ROC-AUC with DeLong confidence intervals, a full confusion-matrix metric suite, precision-recall AUC, Brier score, and calibration and learning-curve diagnostics, on training, cross-validation, internal-test, and external-test data in turn. The tabs connect through shared reactive state: Data & Setup fixes the cohort and contrast; Feature Source and Filters & Parameters configure every subsequent model run; each model tab records its test-evaluated performance into a shared run history consumed by Model Comparison and Export. This implementation matters because it lets a methylomics-focused user compare six standard supervised algorithms on a curated CpG panel under a consistent, leakage-audited evaluation protocol, while transparently disclosing where the module's own feature-panel provenance could optimistically bias its internal test estimate.

## 29. Very Brief Thesis Version

The Diagnostic Classifier submodule trains six supervised classifiers (logistic regression, elastic net, SVM, random forest, XGBoost, k-NN) on DNA methylation M-values at a curated CpG panel to discriminate a disease phenotype from controls, using cross-validated hyperparameter tuning and evaluation on held-out internal and, for the female stratum, an independent external cohort. Methylation features are converted from beta- to M-values by a fixed logit transform before a stratified train/test split, and CpG panels are imported from published WGCNA or feature-selection results, an uploaded list, or manual choice rather than selected live within the module. Performance is reported via ROC-AUC with confidence intervals, a full confusion-matrix metric set, calibration, and learning curves, with an explicit, code-present caveat that internal test estimates can be optimistically biased when the feature panel's original selection cohort overlaps with this module's own test split. This provides a transparent, reproducible framework for comparing candidate methylation-based diagnostic panels and algorithms under a single, consistent evaluation protocol.

## 30. Final Conclusion

The Diagnostic Classifier submodule is a well-structured, internally consistent implementation: its six models share one generic fitting/evaluation/plotting pipeline, its cross-validation and scaling choices are algorithm-appropriate and leakage-safe, its threshold selection is always derived from training data, and it transparently discloses its own most significant methodological risk (cross-cohort feature-panel provenance) directly in the UI. Its principal gaps are consistency gaps rather than correctness gaps: imbalance handling behaves differently across model families without disclosure, one threshold strategy can silently fail its stated target, and several diagnostic computations (Platt calibration) are implemented but never connected to any user-facing effect. None of these issues invalidate the reported AUCs or confusion-matrix metrics themselves; they affect specific secondary behaviors (threshold edge cases, imbalance-handling uniformity, calibration correction) that a thesis or publication drawing on this module's output should acknowledge explicitly, particularly the small, female-only external validation cohort as the basis for any generalization claim.

## What I Should Understand After Reading This Module

1. **What it does:** fits and evaluates six different supervised classifiers to distinguish a disease phenotype from controls using DNA methylation at a chosen CpG or CpG panel.
2. **What data it receives:** either a preloaded, already-normalized 21-CpG panel dataset (with a small independent external cohort for females) or a user's own uploaded methylation matrix and sample sheet.
3. **What happens first:** the data is filtered to the chosen sex/class contrast, converted from beta-values to M-values, and split — once, with a fixed seed — into training and test sets.
4. **What normalization/preprocessing occurs:** only the beta-to-M-value transform, which is a fixed, per-value calculation and therefore does not leak information between train and test; no additional batch correction or imputation is performed, and problems like missing values or near-zero-variance features are reported but not fixed automatically.
5. **How features are selected:** they are not selected inside this module at all — they are imported from an already-computed WGCNA module list, an already-computed feature-selection vote table, an uploaded list, or picked by hand.
6. **How the classifier is trained:** using cross-validated hyperparameter search on the training data only, with scaling applied only to the algorithms that need it (SVM, k-NN).
7. **How predictions are produced:** a single shared prediction function converts any of the six fitted models into a predicted probability for each sample, used consistently for training, cross-validation, and test evaluation.
8. **How performance is evaluated:** ROC-AUC with confidence intervals, a full set of confusion-matrix-based metrics, precision-recall AUC, calibration curves, and a learning curve — always keeping training, cross-validated, internal-test, and external-test numbers visually separate.
9. **How the tabs are connected:** Data & Setup feeds everything; Feature Source and Filters & Parameters configure every model run; each model's completed run feeds the Model Comparison and Export tabs.
10. **What the final result means biologically:** an estimate of how well methylation at the chosen CpG(s) can diagnostically separate the disease and reference groups, with the external-cohort AUC being the most trustworthy number when the panel came from WGCNA or Feature Selection.
11. **What the major limitations are:** a small, female-only external cohort; no live feature selection or automatic correction of data-quality issues; inconsistent imbalance-handling behavior across models; and a threshold strategy that can silently miss its target.
12. **What should be corrected before using these results in a thesis or publication:** explicitly state the external-cohort sample size and sex restriction wherever "external AUC" is reported; verify, for any WGCNA/Feature-Selection-sourced panel, that reported "test AUC" is clearly labeled as potentially optimistic; and confirm which imbalance-handling setting was actually in effect for whichever model(s) results are drawn from, given the "weighted"/"SMOTE" behavior differences documented in §14 and §24b.
