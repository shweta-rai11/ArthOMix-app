# Table S2 — Transcriptomics pipeline: methodology decision guide

*Companion to `ArthOMix_BioinfAdv_ApplicationNote_Supplementary_template.md` (§S4). Built 2026-09-08 by reading every submodule in `R/transcriptomics/` in full (17 files) and extracting every user-facing control that changes which statistical method/model runs, or how it's parameterized — grounded strictly in the app's own code (validation messages, tooltips, comments) rather than invented rationale. Every row below is traceable to a `file:line` in the codebase. Purely cosmetic UI (plot colors, axis pickers) is excluded.*

**How to read this table.** For each control: what the options mean, what the app actually does differently for each, and — critically — *when to pick which and why*, quoting the app's own guidance text where it exists. Where no such guidance exists in the code, this is stated explicitly rather than invented, per the same standard the rest of this paper's numbers were held to.

## 3. Preprocessing and Batch Correction

| Control | Options | What it does | When to use which, and why | Source |
|---|---|---|---|---|
| **Log2 Transform** | Auto-detect (recommended) / Force / Skip | `auto`: log2-transforms only if the 99th percentile of positive values > 100. `force`: always. `skip`: never. | **Auto** — "Log2-transforms the data only if it looks untransformed... use this unless you have a reason not to." **Force** — "Use only if you're sure the data is raw and auto-detect got it wrong." **Skip** — "Use for raw RNA-seq counts that will be normalised downstream (e.g. TMM, DESeq2), or data that's already log-scaled." | `mod_preprocessing.R:19-27` |
| **Merge mode** | Merge example pipeline's training datasets / Merge your own data | On the default group selection, the "example" path takes a **fast shortcut** straight to the app's precomputed, already-batch-corrected default cohort instead of re-merging raw data live. | Disclosed explicitly: *"Uses the real merged, already-batch-corrected training cohort directly (fast), so Batch Correction below will find little or no residual batch effect left to remove."* Not a bug — expected behavior on the default combination. | `mod_preprocessing.R:583-585, 637-693` |
| **Collapsing method** (probe→gene) | Median across probes (recommended) / Highest-mean probe (this app's preloaded convention) / Mean across probes | `median`: matches most published methods (cites Zhu et al. 2021). `maxmean`: matches how this app's own bundled cohorts were built. `mean`: plain average. Multi-mapped probes are always dropped, never split. | Use median for general reproducibility with the literature; use "highest-mean probe" only if you specifically need parity with this app's bundled reference datasets. | `mod_preprocessing.R:43-64, 517-527` |
| **Normalisation** | Auto-detect / Already normalised, skip / Quantile (microarray or log-scale) / TMM + log2-CPM (RNA-seq raw counts) | `tmm` requires non-negative, ≥99%-near-integer values (else blocked with a specific message pointing at Log2=Skip). **`quantile`/`auto` are hard-blocked on data that looks like raw counts** — "Quantile normalisation assumes already-comparable per-sample distributions... Choose 'TMM + log2-CPM' instead." | Use **TMM+log2-CPM** for RNA-seq counts (and set Log2=Skip beforehand — it uses its own `edgeR::filterByExpr()` gene filter instead of the percentile slider). Use **Quantile** for microarray or already-log-scale data. Use **Skip** if normalized elsewhere. | `mod_preprocessing.R:956-966, 1124-1247` |
| **Batch-correct raw counts, or normalised log2-CPM?** (only when Normalisation=TMM) | After TMM: ComBat/limma on log2-CPM (typical) / Before TMM: ComBat-seq on raw counts (Zhang, Parmigiani & Johnson 2020) | `pre` runs negative-binomial ComBat-seq before TMM — better for large, count-driven batch effects. | ⚠️ **Choosing "pre" silently disables** the Correction method / prior / reference batch / exclude-outliers controls below (disclosed in a static note, but those widgets stay visibly interactive) — always uses batch column + covariates only, protects group automatically. | `mod_preprocessing.R:975-984, 1144-1200` |
| **Correction method** | ComBat (empirical Bayes, recommended) / limma::removeBatchEffect (simple linear) / SVA (unknown/hidden sources, no batch column needed) | `combat`: parametric/non-parametric empirical Bayes, with cascading automatic fallback on failure (drops interaction batch → drops covariates, each logged). `limma`: simpler linear adjustment. `sva`: estimates hidden surrogate variables directly from data, not tied to a batch column. | **SVA** — *"Useful when the real source of batch effects is unknown or only partly captured. Still protects the covariates chosen below."* (Leek et al. 2012). No comparable in-app guidance distinguishes ComBat vs. limma beyond the label text. | `mod_preprocessing.R:992-1009, 1300-1354` |
| ComBat empirical Bayes prior | Parametric (faster, default) / Non-parametric (slower, more robust for small/uneven batches) | — | Use non-parametric only for small or uneven batch sizes, per the label itself. | `mod_preprocessing.R:1000-1002` |
| Confounding block/override | Blocked unless overridden | Chi-square test (`multi_live_confounding_check`) blocks the run if batch and group are strongly associated — *"Correction may remove real biological signal and can't reliably separate batch from phenotype."* | Override only if you understand the risk; the app's own alternative suggestion is *"choose SVA or a different batch column"* — SVA is exempt from this gate since it doesn't use the batch column. | `mod_preprocessing.R:1026-1067, 1100-1109` |
| **Study-wise Meta-analysis** (alternative to Batch Correction entirely) | — | Fits **one limma model per study** (auto TMM+voom if that study looks like counts, else auto quantile-norm if needed), then pools via DerSimonian-Laird random-effects meta-analysis, BH-FDR across genes. No batch correction applied at all. | *"For studies too different to pool - analyse each separately, then combine effect sizes... Cost: lower power than a compatible pooled analysis."* With only one qualifying study, the app redirects: *"use the Batch correction tab instead."* | `mod_preprocessing.R:151-229, 1753-1830` |

## 4. Differential Expression

| Control | Options | What it does | When to use which, and why | Source |
|---|---|---|---|---|
| **Method** | limma (microarray, log-scale, or already-normalised data) / DESeq2 (RNA-seq raw counts) | DESeq2 blocked unless data is genuinely raw non-negative integer counts (`is_counts`); also blocked if it has TPM/FPKM/CPM-pinned totals even if superficially count-like. limma blocked if data is raw, un-normalized counts. | **This is the exact decision point this session hit live** with GSE77298 (MAS5 array data mistakenly loaded unlogged): the error *"some values in assay are negative"* traced back to DESeq2 being fed log-transformed data through this path. Fix: declare Data Type correctly at upload (§1) and pick the method matching your data's true origin — DESeq2 for genuine sequencing read counts only, never for microarray intensities regardless of value range. | `mod_dge.R:307-314, 404-419` |
| Auto log2-transform inside limma | — (automatic, not user-visible until after running) | If data is linear-scale normalized (TPM/FPKM/CPM) rather than raw counts, limma **silently** applies `log2(x+1)` before fitting — because fitting linear-scale data directly "understated large fold-changes and produced a logFC that wasn't actually log2-scale despite the volcano axis unconditionally labelling it 'log2 fold-change'." | Disclosed only *after* the run, appended to the test-label text: *"input was linear-scale normalised expression, log2(x + 1)-transformed before fitting."* Not something you choose — but check this label to confirm your data was handled as you expected. | `mod_dge.R:420-426, 480-482` |
| **Second column: Filter vs. Adjust** | Filter to one level of this column / Adjust for this column as a covariate | `filter` subsets to one covariate level before fitting; `adjust` adds it as an additive design term. | ⚠️ **No guidance exists anywhere in the app for this choice** — unlike nearly every other control here, this radio group has zero tooltip/hint text. State this gap plainly rather than inventing advice: use "Filter" when the covariate is confounded with the contrast or has too few samples per cell to estimate; use "Adjust" when you have enough samples per covariate level to estimate its effect independently. | `mod_dge.R:336-343` |
| **How the fold-change cutoff is applied** | Filter after testing (post hoc) / limma::treat (fold-change inside H0, McCarthy & Smyth 2009, limma only) | `posthoc`: test against log2FC=0, then apply `\|log2FC\|` gate afterward. `treat`: tests `H0: \|log2FC\| ≤ cutoff` directly — more conservative. | Exact in-app guidance: *"A \|log2FC\| cutoff of 0.1 (a 1.07-fold change) is a coherence filter, not a prioritisation step - it calls about half the transcriptome significant on the bundled cohort. The result panel also reports counts at 0.5 and 1.0, so this choice's effect stays visible."* ⚠️ Selecting "treat" under DESeq2 is **silently ignored** (label says "limma only") with no runtime warning — results are quietly computed post hoc instead. | `mod_dge.R:108-117, 356, 462-464` |

## Documentation/UI issues surfaced by this audit — status as of 2026-09-08

These were found as a byproduct of building this table, not the table's primary purpose — but they materially affect the accuracy of what the app tells a user. Each was independently re-verified (algebraically or with the existing test suite) before being fixed, and one initial finding was retracted after verification rather than "fixed" incorrectly.

1. ✅ **FIXED — stale statistical-criterion text.** `mod_candidates.R:129` stated the WGCNA disease-module pre-selection rule as "\|cor\| ≥ 0.5, p < 1e-8"; the actual, current rule (`mod_wgcna.R:37-47`, which documents its own correction away from exactly this kind of uncorrected substitute) is \|cor\| ≥ 0.5 **AND BH-FDR q < 0.05**. Text corrected to match the code.
2. ❌ **RETRACTED — not a bug.** Initially flagged: "Cross-Tissue 'replicated' badge uses best-direction AUC even when the displayed plot is switched to train-fixed orientation." Verified algebraically (`ct_discovery_table`, `mod_crosstissue.R:63-67`): `auc_trainorient` is defined to equal `auc_bestdir` exactly whenever `concordant==TRUE`, and `ct_biomarker_flag()` already requires `concordant==TRUE`. The two AUC fields are provably identical in every case the badge can be TRUE. No code change made.
3. ✅ **FIXED — silent no-op on `limma::treat` + DESeq2.** `mod_dge.R` now appends an explicit note to the result's test-label when a user selects "treat" but Method=DESeq2 (the request is limma-only and was being silently dropped): *"'limma::treat' was requested but ignored (limma-only); the \|log2FC\| cutoff was applied post hoc instead."*
4. ✅ **FIXED — reference batch silently ignored with an interaction batch column.** `mod_preprocessing.R`'s `ref_batch_ui` now hides the Reference batch selector (with an explanatory note) whenever a second/interaction batch column is set, instead of leaving it visibly interactive with no effect.
5. ✅ **FIXED — ComBat-seq (pre-TMM) silently disabling visible "advanced" controls.** The Correction method / prior / mean-only / reference-batch / exclude-outliers controls in `mod_preprocessing.R` are now hidden (replaced with an explanatory note) whenever "Before TMM: ComBat-seq" is selected, rather than staying interactively visible while having no effect. `batch_col2` and the variance-percentile filter remain visible, since ComBat-seq genuinely does use them.
6. ✅ **FIXED — incomplete WGCNA settings-summary disclosure.** `mod_wgcna.R`'s pre-fill note now also states the TOM-type (signed) and PAM-respects-dendrogram defaults, alongside the power/min-module-size/merge-cut-height it already listed, and notes the reference cohort's network was built without PAM respecting the dendrogram.
7. ✅ **FIXED (root cause) — the shared raw-counts/linear-scale detection heuristic.** `looks_like_raw_counts()` (`functions/expression_type.R`) now additionally requires ≥99% of values to be near-integer (reusing the exact tolerance already established by TMM's own upload validation), not just "non-negative with a wide dynamic range." This directly fixes the false-positive class that caused the GSE77298 incident this session (linear-scale MAS5 microarray intensities being misclassified as raw sequencing counts) — and fixes it once, at the shared root, rather than patching each of its 6 call sites (Preprocessing, DGE ×2, Overview/QC, Immune Deconvolution) separately. Verified with a direct unit test: genuine integer counts still classify as counts; non-integer linear-scale data (MAS5-like) and log-scale data both correctly classify as not-counts. One knock-on fix was needed in `mod_dge.R`: the DESeq2 validation order was swapped so the more specific "this looks like CPM-normalized data" message is checked before the newly-stricter generic "not raw counts" message, so CPM-normalized uploads (non-integer by construction) still get the more informative of the two messages. Full existing test suite (`txn-expression-type`, `txn-dge`, `txn-preprocessing-*`, `txn-wgcna-*`, `txn-candidates`) passes after this change with zero failures.

**Freeze note**: these are minimal, additive/UI-scoped changes (warning text, hiding a widget when it has no effect, tightening one shared heuristic to reject more false positives) — no change to any of the 4 frozen case studies' actual computed numbers, since all 4 explicitly declared their Data Type at upload, and `looks_like_raw_counts()` is only ever consulted as a *fallback* when no explicit declaration exists. The case-study freeze tag (`paper-case-studies-freeze-20260908`) was, however, already broken by an unrelated prior commit (`c44c384`, the Excel gene-symbol repair) before this session started — so the 4 case studies should be re-verified in the browser against current `HEAD` regardless of today's changes, not because of them.
